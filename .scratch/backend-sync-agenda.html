Frontend ↔ Backend Alignment Sync

The Next.js frontend was built directly against the Development Document v1.1 FRD, running on a mock API layer. Before we wire it to the real FastAPI service, two structural questions need answers, and a handful of type-shape gaps need reconciling.

Product Solar Site Fitness & Capacity Engine Frontend status Three portals scaffolded, building clean, running on mock data Backend status In progress

01Why this sync

The frontend's types (web/lib/types.ts) were written to mirror the FRD's response shapes as closely as possible — verdicts, capacity/confidence/binding-constraint, the cache and vision-refinement fields, etc. Most of it should map cleanly. But two things came up while reconciling the frontend against the FRD that are architectural, not cosmetic, and are worth settling before more code gets written on either side.

02The two questions that matter most

Question 1 — Auth model

The FRD's API-06 specifies auth by API key scoped to a tenant — a B2B model, where a tenant is a state agency, RESCO, DISCOM or corporate account. The Customer-facing frontend we built is a consumer email/password signup flow for an individual homeowner checking their own rooftop. Those are two different auth models. Is the consumer flow meant to sit on top of the tenant/API-key model (one household = one tenant, provisioned automatically on signup?), or is it out of scope for what this FRD covers and needs its own spec from your side?

Question 2 — Is there a Vendor / field-service API?

The FRD states plainly: "Registry, dashboards and survey workflow are packaging: specified in v1.0, optional per deployment, and omitted here." The Vendor portal we built (job assignment, accept/decline, SLA tracking, payouts, disputes) has no counterpart anywhere in the v1.1 document — it was our own extrapolation to fill a gap, flagged as the single biggest assumption when we scoped it. Does this exist in the separate v1.0 spec/registry doc? If not, it needs scoping from scratch before the vendor portal can be wired to anything real.

04Already aligned — low-risk to wire up

  • Verdict enum: SUITABLE / SUITABLE_SUBJECT_TO_SURVEY / CONDITIONAL / INSUFFICIENT_DATA / NOT_SUITABLE — exact match to FIT‑02.
  • Site types: ROOFTOP_GOVT / ROOFTOP_RESIDENTIAL / ROOFTOP_CI / FLOATING — matches SITE‑03's minimum set.
  • Assessment shape (capacity, confidence, binding constraint, reasons, ceiling ledger) — matches FIT‑04/05/06 and CAP‑02/05.
  • Optional additive fields (visionRefinement, panoramaUrl, mlSuitabilityScore) — match API‑01's "additive, never required" language.
  • Admin-portal concepts — jurisdiction packs, ML model approval queue, calibration proposals with propose-then-approve status — map cleanly to CFG, ML‑04, CAL‑03.
