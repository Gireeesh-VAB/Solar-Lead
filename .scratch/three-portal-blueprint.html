Customer, Vendor & Super Admin — Portal Blueprint

Three purpose-built experiences on one platform: the organisations that buy site assessments, the field teams that fulfil them, and the internal team that runs the whole system.

● Customer Portal ● Vendor Portal ● Super Admin Portal
Builds on the Solar Site Fitness & Capacity Engine, Dev. Doc v1.1 Status Architecture — no screens designed yet Scope UX strategy, IA, screens, permissions, shared system
01

The Three User Types

Mapped from the source document's actual roles — not invented from scratch
Framing assumption — the one to validate first

The source document is written around five buyer segments (state agencies, RESCOs, DISCOMs, corporates) plus one internal field/geometry operator role — it doesn't use the words "customer," "vendor" or "super admin" natively. This blueprint maps that structure onto the three-portal architecture as follows: Customer = the tenant organisations who buy and consume site assessments (all five buyer segments, unified into one portal experience). Vendor = the field geometry/survey service providers who fulfil the manual capture and boundary work the platform assigns, paid per site, with quality tracked against the calibration system. Super Admin = the platform operator's own internal team, governing every tenant, every vendor, every constraint pack and every ML model. This is the single largest interpretive decision in the whole blueprint — confirm it matches the actual business model before screens are built.

Customer

Who: procurement/technical leads at state agencies, RESCO bid teams, DISCOM programme cells, corporate sustainability heads — organisations, represented by named users with seats.

Wants: a defensible, ranked list of viable sites and capacity, fast, exportable, trackable over time.

Common tasks: add/import sites, review a verdict, drill into evidence, export a report, track assessment status, manage team seats.

Cares about: verdict, capacity, confidence, binding constraint, portfolio saturation, cost against budget.

Immediately after login: what changed since last visit — new results ready, anything flagged low-confidence, portfolio summary.

Simplify: hide constraint-pack internals, ML scoring detail, and calibration mechanics entirely — plain-language reasons only.

Vendor

Who: individual field surveyors or small survey/geometry-capture firms; potentially EPC/installer partners once a site clears feasibility.

Responsibilities: accept assigned site jobs, visit site, draw/measure boundary, capture USN evidence, submit within SLA.

Workflow: job queue → accept → travel → capture → submit → reconcile against remote estimate → get paid.

Manages: assigned jobs, submission history, payout/earnings, accuracy score.

Frequent actions: check queue, submit field boundary, submit USN, mark complete.

Metrics that matter: jobs this week, turnaround time, accuracy/variance score, earnings.

Optimise for: speed in the field, minimal typing, camera-first capture, tolerant of poor connectivity.

Super Admin

Controls: tenant accounts (create/tier/suspend), vendor accounts (onboard/verify/deactivate), jurisdiction & constraint packs, ML model approval, parameter packs, billing, API keys/quotas, feature flags.

Operational data needed: cross-tenant usage, assessment volume, error/failure rates, cache-hit rate (proof of cost efficiency), vendor SLA compliance, revenue.

Management: approve/hold a new ML model version, approve calibration factor changes, resolve billing/USN disputes, impersonate a tenant for support.

Monitoring: platform health, third-party API quota (Maps/Solar API/GPT‑4 Vision/Weather), full audit log of every admin action.

High-level metrics: total tenants, total sites assessed, active vendors, MRR, uptime, open exceptions.

03

Customer Portal — Mobile-First

Mobile is the primary design target, not a fallback

Mobile navigation pattern

● Recommendation

Bottom navigation, 4 items: Home, Sites, Notifications, Profile. This fits the customer's actual workflow — a handful of top-level destinations visited repeatedly, not a deep catalogue needing a hamburger drawer. A hamburger menu would hide "Sites" (the single most-used destination) behind an extra tap, which is wrong for a product where checking on a portfolio is the core habit loop.

Inside Sites, use a top tab bar (All / Suitable / Needs Review / Insufficient Data) rather than a filter drawer for the primary triage — it's the customer's single most common decision and deserves a persistent, one-tap surface, not a modal.

Bulk actions

Minimal by design — vendors work job-by-job in the field. The one bulk action worth building: accept/decline multiple queued jobs from the desktop queue view before heading out for the day.

Search by site name/ID/address; filter the queue by distance, deadline and site type. No saved-filter complexity needed — the queue is small enough to scan.

When to use which data pattern

Table vs. drawer vs. page

Table for any list exceeding ~10 comparable rows. Drawer for a quick look that needs zero navigation cost (tenant summary, vendor summary). Full page when the detail itself is a workspace (an assessment's full evidence, a jurisdiction pack's diff).

Bulk actions

Reserved for genuinely repetitive admin work — bulk-verify a batch of vendor onboarding submissions, bulk-suspend flagged accounts — always behind an explicit confirm listing exactly what will change.

Charts vs. tables

Charts for trend/proportion at a glance (usage over time, tier distribution); tables the moment a user needs to act on an individual row. Never a chart as the only way to reach a record.

Export

Present on every data-heavy screen as a persistent, unambiguous action — admin work routinely leaves the product for spreadsheets, board decks and compliance reviews.

Hide, not disable

Anything a role has no legitimate reason to know exists — a customer never sees a "Manage Vendors" nav item, disabled or otherwise. Cross-tenant admin functionality is invisible outside the Super Admin portal entirely, not gated behind a locked button in the same UI.

Disable + explain, don't hide

Reserved for in-context, expected actions the current user almost took but can't complete right now — a vendor's "Submit" button disabled with "Verification pending" until onboarding clears; a customer's "Force refresh" disabled with "Contact support" if that action is admin-gated per tenant policy.

09

Shared Design System

One ecosystem, three calibrations

Neutrals, semantic verdict colors, typography and the base component shapes are identical everywhere — that's what makes this one product. Each portal then carries its own accent and its own density calibration of the same components, never a different visual language.

Customer accent — Amber

Warm, the platform's primary brand color. Larger touch targets, more generous spacing, rounded-but-still-precise radii (5–8px), lower density.

Vendor accent — Teal

Signals "active/efficient/go." Medium density, tuned for fast scanning and one-handed mobile use — compact cards, prominent single primary action per screen.

Admin accent — Slate

Cool, desaturated, authoritative. Tightest density, smallest consistent radii (3–4px), monospace numerals everywhere a figure appears.

FoundationShared across all three
TypographyIBM Plex Sans (UI/headings), IBM Plex Mono (every number, ID, coordinate, currency figure — tabular numerals). No serif in-product.
Base neutralsPaper/surface/ink scale identical across portals — the "ground" never changes, only the accent painted on top of it.
Semantic statusVerdict palette (good/warn/bad/neutral) is platform-wide and portal-agnostic — a SUITABLE verdict is the same green whether a customer, vendor or admin is looking at it.
SpacingShared 4px base scale; each portal picks a different point on it as default (Customer generous, Vendor medium, Admin tight) — never a different scale.
Grid & breakpointsSame breakpoint set (640/900/1200/1440) everywhere; how aggressively each portal collapses at each one differs (Admin resists mobile collapse the longest).
RadiusShared small-radius philosophy (3–8px range); Customer sits at the soft end, Admin at the sharp end.
Shadows/elevationReserved for floating layers only, identical rule in all three portals.
IconographyOne line-icon set, single stroke weight, shared across all three — never a friendlier icon style for Customer and a technical one for Admin.

Visual Hierarchy by Portal

Personality, adjusted to what this specific product actually needs from each role
Customer feels:

Simple, trustworthy, clear, modern, effortless — but not casual. This is a professional buying a defensible technical answer, not a consumer app; "friendly" here means low-friction and plain-spoken, not playful.

Vendor feels:

Professional, efficient, operational, clear — closer to a field-service or logistics app than an office dashboard. Every screen answers "what do I do right now."

Super Admin feels:

Powerful, structured, precise, reliable, information-dense — closer to a network operations console than a SaaS admin panel. Nothing here is trying to look approachable; it's trying to look correct.

Responsive Strategy, Per Portal

Not one strategy applied three times
● Customer — Mobile-first

Every screen designed at 375px width first, then expanded. Breakpoints: mobile <640, tablet 640–1199, desktop ≥1200. Mobile is a primary, fully-featured experience — not a reduced view. Desktop adds density (tables instead of cards, side-by-side map+panel) but adds no functionality mobile lacks.

● Vendor — Responsive, mobile-critical for field tasks

Job queue, job detail, boundary capture and USN capture must work excellently on phone/tablet — these happen on-site, often outdoors, sometimes on poor connectivity. Earnings, performance history and settings are fine as desktop-first, responsive-but-not-optimised screens — a vendor reviewing payouts is more likely at a desk than in the field.

● Super Admin — Desktop primary, tablet supported, mobile monitoring-only

Desktop is the only real working surface — dense tables, multi-panel comparisons and bulk actions do not survive a small screen without destroying usability, and this is exactly the audience for whom bad usability has the highest cost. Tablet gets a workable, somewhat-simplified version of the same screens. Mobile is deliberately limited to monitoring only: the dashboard, exception alerts, and third-party API status — enough to know something needs attention, never enough to configure the platform from a phone.

14

UX Quality Standards & Risks to Design Around

Problems identified before UI design begins
Customer risk

A team-seat customer with low technical literacy may not understand "confidence" or "binding constraint" without a first-touch explainer — plan a one-time contextual tooltip on first view, not a manual.

Vendor risk

Field connectivity is unreliable — any capture flow that loses work on a dropped connection destroys trust immediately. Offline-first draft saving is not optional polish, it's a correctness requirement.

Admin risk

Power without friction is dangerous here — a suspend/publish/approve action taken by mistake affects other people's businesses. Every irreversible admin action needs a real confirmation step, and the audit log must be unimpeachable (append-only, no admin — including the platform's own developers — can edit it from the UI).

  • Consistency risk: reusing the verdict/status vocabulary exactly (not "Approved" in one portal and "Verified" in another for the same underlying state) so a customer and a support admin looking at the same record aren't confused by different words.
  • Cognitive load risk (Admin): the temptation to put everything on one dense dashboard — mitigated by the "every tile links to what it's warning about" rule in §12, so density serves triage rather than decoration.
  • Workflow efficiency risk (Vendor): too many taps between "open app" and "start capturing" kills adoption for a paid-per-job workforce — the dashboard's one-tap "start next job" exists specifically to remove this friction.
  • Accessibility risk (shared): map-based interactions (customer's portfolio map, vendor's boundary capture) need a non-pointer fallback in all three portals per the same discipline as the single-portal engine blueprint — address/coordinate entry as an alternative to drawing.
15

Designing the Ecosystem

Connected without being identical
Shared brand layer

One wordmark, one typographic system, one neutral palette, one icon set, one verdict/status vocabulary. A screenshot from any portal should be immediately recognisable as the same product family.

Portal layer

Customer → consumer-grade simplicity on top of that brand. Vendor → business/operations efficiency on top of that brand. Super Admin → platform-control precision on top of that brand. The accent color, density and navigation pattern are the only things that change — never the underlying grammar of type, spacing units, or how a status is communicated.

A useful test: a user moving between portals (a support admin viewing a tenant's data, for instance) should feel like they've walked into a different room of the same building — not a different building entirely.

Recommended Design Order

Sequenced by actual dependency, not by portal importance
  1. Product UX foundationConfirm the customer/vendor/admin mapping in §1 against the real business model before anything else — everything downstream depends on this being right.
  2. Shared design systemTokens, type scale, spacing, the verdict/status vocabulary, base component shapes — built once, before any portal-specific screen.
  3. Authentication & role routingLogin, role detection, portal routing — every portal needs this before it needs anything else.
  4. Customer core journeyHome → Site List → Site Detail → Add Site. The highest-volume, most-validated flow, and the one most similar to work already scoped for the single-portal engine.
  5. Customer mobile experienceApply the mobile-first patterns from §3 to the core journey before moving on — retrofitting mobile later is exactly what this brief said not to do.
  6. Vendor core workflowJob Queue → Job Detail → Boundary/USN Capture. This is the operational backbone the whole supply side depends on.
  7. Vendor dashboard & earningsLower urgency than the capture flow, but needed before a vendor workforce can be onboarded for real.
  8. Super Admin architectureIA, navigation, and the dense-table/drawer/page patterns from §5 — admin work depends on customer and vendor data models being stable first, which is why it comes after both.
  9. Admin data-heavy workflowsTenant/vendor management, assessments table, jurisdiction packs, model approval — built on the architecture from step 8.
  10. Shared statesEmpty/loading/error/confirmation, applied per-portal per §13 — across everything built in steps 4–9.
  11. Responsive refinementTablet behaviour for all three, and the mobile-monitoring slice of Super Admin.
  12. Accessibility passNon-pointer map fallbacks, contrast audit on all three accent/verdict combinations, keyboard and screen-reader pass.

Final Deliverable — Three-Portal Blueprint

The single reference to build from
A. Customer Portal

Mobile-first, low-density, trust-building. Home digest, site list/detail, add/import, portfolio map, reports, team, billing. Bottom-nav mobile pattern, full parity with desktop.

B. Vendor Portal

Operational, task-completion-first. Job queue, capture flows, submission history, earnings, performance, service area. Mobile-critical for field capture, desktop-supported for admin-of-self tasks.

C. Super Admin Portal

Control-center, dense, desktop-primary. Tenant/vendor management, platform-wide assessments, jurisdiction/model/calibration governance, reports, audit log, configuration.

D. Shared Design System

IBM Plex Sans/Mono typography, one neutral scale, one semantic verdict palette, shared 4px spacing scale and breakpoint set, small-radius philosophy, floating-only shadows, one line-icon set — each portal applying its own accent (amber / teal / slate) and density calibration on top, never a different visual language.

E. Permission Matrix

See §8 in full. Governing rule: hide functionality a role has no legitimate reason to know about; disable-with-explanation only for in-context actions the current user can see themselves eventually taking.
