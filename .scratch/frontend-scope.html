Frontend Build Scope

Everything the Next.js app needs to build, assuming the FastAPI engine, OpenAPI contract, and background pipeline (vision, 3D, ML, cache) already exist behind it. This is the complete frontend-side work list.

01

What "Frontend Only" Means Here

Drawing the line cleanly so nothing backend leaks into the sprint plan

The backend team owns the engine: geometry providers, constraint packs, the capacity resolver, generation modelling, fitness scoring, vision refinement, 3D generation, ML scoring, the result cache, and the whole PostGIS/FastAPI/Celery stack. We consume all of it through one versioned REST API (API‑01…09) and one generated TypeScript type set. Nothing below assumes we can see inside that boundary — every screen is built against the response shape, not the implementation.

We own

Every route, page, component, client-side state, map interaction, form, chart, and export trigger in apps/web. Client-side geometry math (live area preview only, via Turf) — never authoritative.

We consume, never reimplement

Capacity/verdict computation, constraint evaluation, vision refinement, 3D mesh generation, ML scoring, caching logic, calibration math. If a number needs computing, it comes from the API — we never shadow-calculate it in the browser.

Data Layer

Every API surface the frontend talks to, and how
API requirementFrontend hookPattern
API‑01 assessment shapeuseAssessment(siteId)Single query; optional fields (vision_refinement, panorama_url, ml_suitability_score, cache_hit) rendered conditionally, never assumed present.
API‑02 sync assessmentuseCreateSite()Mutation; on cache hit, response renders instantly with the provenance badge already set.
API‑03 async batchuseBatchJob(jobId)Polling query (interval backoff), or SSE/webhook-fed if the backend exposes one — never a fire-and-forget submit.
API‑04/05 versioningglobal response interceptorEngine/pack version surfaced in a detail-view footer, never blocking the UI.
API‑06 auth & quotalib/authAPI key/session scoped per tenant; quota exhaustion shown as a specific, actionable banner, not a generic 429.
API‑07 bulk importuseBulkImport()Multipart upload + per-row error array rendered as the Import Error Report.
API‑08 exportuseExport(format)Triggers server-generated file; frontend never assembles CSV/PDF client-side.
API‑09 webhookssettings onlyConfiguration UI only — the frontend does not consume its own webhooks.

State management rules

  • TanStack Query owns all server state; no assessment/verdict data duplicated into a global client store.
  • Client-side (Zustand or React context, whichever is already standard) is reserved for pure UI state: map viewport, drawer open/closed, selected rows, draft form values before submit.
  • Optimistic updates are used only for reversible, low-stakes actions (tagging, filter changes) — never for verdict-affecting submissions like boundary promotion.
07

Map & Geometry Layer

The single most complex piece of frontend work in this product
Base map

@vis.gl/react-google-maps, one shared instance/config reused across portfolio map, site detail and boundary editor — not three separate integrations.

Drawing

terra-draw for boundary + exclusion polygon capture; enforce closed-polygon and minimum-vertex rules client-side as immediate feedback, with the server (GEO‑07/08) as final authority.

Live area feedback

@turf/turf computes an approximate area as the user draws — always labelled "approximate," never presented with the precision of the server-computed usable area.

Portfolio-scale overlays

deck.gl for clustering and verdict-colored layers once site counts move into the thousands — a plain marker-per-site approach breaks down well before then.

AI suggestion overlay

Renders the VIS-annotated boundary as a distinct, equal-weight layer beside (not replacing) the provider original — the accept/reject decision needs both visible at once.

Panorama/3D

@react-three/fiber for interactive mesh artifacts, or a flat panorama-image viewer depending on what VIZ returns — the frontend renders whichever panorama_url type it's given, never assumes one format.

08

Cross-Cutting Frontend Concerns

Work that touches every screen, not one
  • Auth & tenant context — session/API-key handling, tenant switcher for multi-org users, route guards on admin-only settings pages.
  • Design tokens as code — the palette, type scale, spacing and radius from the UX/UI Blueprint implemented as CSS variables (light + dark), consumed by every design-system primitive — never a hard-coded hex in a component.
  • Empty / loading / error / insufficient-data states — built once per pattern in the design system, then applied to every list, card and detail view — not re-invented per screen.
  • Notifications — job completion, calibration proposals, model-approval requests surfaced consistently via the header bell + toast pattern.
  • Accessibility — non-pointer path into every geo-selection flow (address/coordinate entry as an alternative to map interaction), verified focus order, and color-paired-with-text on every verdict/status chip.
  • Responsive shell — one workspace layout that collapses sidebar → icon rail → tab-based map/panel as width drops, plus the separate, deliberately minimal (field) route group for mobile capture.
  • Error boundaries — per-route boundary so a failed panorama render or map load never takes down the verdict card next to it.
  • Testing — component tests for the design-system primitives (verdict chip states, confidence tiers), integration tests for the create-site → assessment flow and the bulk-import → job-status flow.

10

Explicitly Out of Scope for Frontend

So nobody accidentally starts building engine logic in the browser
Not ours Geometry & constraints

Water-index extraction, area/setback math, constraint packs, the capacity resolver. We render their output.

Not ours Vision, 3D, ML

GPT‑4 Vision calls, mesh/panorama generation, model training/serving. We render URLs and annotations they return.

Not ours Caching & jobs

The result cache, Celery workers, retraining schedule. We poll job status and display cache_hit — we don't implement either.

The one rule that keeps this boundary honest

If a screen needs a number the API doesn't already return, the fix is a backend ticket, not a client-side calculation. The frontend's job is to make the engine's output legible and fast to act on — never to quietly reproduce the engine.
