05

karthik — detailed build plan

All three streams, drilled from an endpoint list down to something an engineer — or an agent — can build directly from: exact tables, exact routes, exact gotchas found across three passes. Karthik's foundation comes first since the other two lean on it.

In plain terms

Login & accounts
Right now nobody can actually log into the app. This builds real sign-up and login, and settles what a "customer account" is — just one person's row in a table, not a company with sub-users.
Site pages
Makes the site data the app already has show up the way its screens expect — name, address, a map location, its full history of changes, and the ability to group several sites into one feeder-level report.
Upload tracking
Uploading a batch of sites today runs once and hands back one final result. This adds the ability to check on an upload while it's still running and look back at past ones.
Activity log & admin basics
A record of who did what (approved a vendor, suspended an account), plus a first pass at system health and credential rotation — honestly limited where the real data doesn't exist yet, not faked.

omkar — detailed build plan

Assessment, USN, calibration/ML, and admin vendor oversight — the stream with the most real backend logic already built, and the most careful frontend-shape mapping to get right.

In plain terms

Real assessments, secured
Makes the "run an assessment" screen call the real engine instead of a random-number generator, and saves the result so it can be looked back on later — by the customer, and by admins across every account.
Utility bill capture
The logic to read a bill and pull out an account number is already built — this just gives the app screens a way to actually reach it.
Approving proposed changes
Right now the system can suggest "this number should change" but nobody can actually say yes — this adds the approve/reject step for both calibration adjustments and new ML model versions.
Admin oversight of vendors
Suspending a vendor, approving a new one, reviewing the sign-up queue — the admin-facing half of the vendor system keerthana builds.

Real mapping gaps — flagged, not guessed at
  • confidence: High|Medium|Low|N/A ← the backend only has a raw 0–1 number. No threshold exists anywhere today — this plan sets one explicitly: N/A when there's no score, High ≥ 0.7, Medium ≥ 0.4, else Low.
  • bindingConstraint:{name,reason,kind} ← the backend only has a bare constraint name string. Found by matching it against the full ceiling list to pull its reason/kind.
  • visionRefinement.deltaKwp — the backend has no such number at all. Returned as a documented placeholder, not invented.
  • generation:{p50AnnualKwh,p90AnnualKwh} — unimplemented backend-wide (confirmed earlier this session). Omitted entirely rather than sent as zero — the frontend type is optional for exactly this reason.
  • cache.originalDate ← needs a second lookup, of the original cached analysis, not the current call's own timestamp.

08

Closing the loop across all three

Every gap found and closed across all three passes

  1. AuditLogEntry.details is a plain string in the frontend type — first draft had it as JSON.
  2. CompositeSite.aggregateCapacityKwp and PortfolioSummary.activeJobs both need cross-stream reads the first draft's dependency list missed.
  3. Login had no brute-force protection — now reuses the existing rate limiter instead of leaving it open.
  4. Signup had no duplicate-email or minimum-password handling.
  5. CORS was mentioned but not specified precisely enough to build safely.
  6. No shared test fixture was planned for the other streams' auth-gated routes — the exact kind of small inconsistency that caused this session's earlier merge friction.
  7. The users table had no owner_org field — without it, nothing, including karthik's own site endpoints, had any way to scope "this customer's data." The single biggest correction this pass, caught only by checking keerthana's work against karthik's already-"finished" schema.
  8. Assessment's frontend shape and the real backend response don't line up on confidence, binding constraint, or generation/vision-refinement fields — each given an explicit mapping or explicit omission instead of a silent guess.
  9. CalibrationProposal's frontend shape and the backend's real model track different things — flagged as a product question.
  10. No creation path exists anywhere for a vendor_job — flagged as an open gap rather than assumed away.
  11. ModelVersionProposal.changelog has no backend field — needs one small additive column.
  12. Three separate "no real metering exists" spots are now handled the same honest-placeholder way instead of each being solved differently.
Next steps for the team
  1. karthik implements his slice first — auth foundation above everything else, since users (with owner_org), write_audit_log(), and the shared test fixture are load-bearing for the other two.
  2. omkar and keerthana start their own table/schema work in parallel, not waiting on karthik — vendors/vendor_jobs, assessments, the calibration/ML approval functions don't need his foundation to exist yet, only the final auth-gating and audit-logging lines do.
  3. Cross-reads get wired last: karthik's history/portfolio-summary endpoints (need omkar's assessments and keerthana's vendor_jobs), omkar's admin-vendor-oversight (needs keerthana's vendors), keerthana's customer-account admin (needs karthik's users).
  4. Migration order: whoever lands first sets the new head; everyone else rebases their down_revision onto it before merging — the same protocol that resolved this session's earlier 4-way branch merge, applied proactively this time.
  5. Once all three are merged: run the full suite together, confirm a single alembic head, and do one combined manual pass — signup → login → create a site → run an assessment → see it in history/portfolio-summary → assign a vendor job → approve it as admin.
  6. Frontend wiring is the step after that, not part of this round — once the backend matches lib/types.ts, rewrite lib/api/client.ts to call it for real, and connect the login/signup forms. Its own follow-up plan.
09

Ground rules

What holds this together

  • Nothing existing changes. All three current routers, their response shapes, and their tests stay exactly as they are. Every new endpoint lives in new files under a new /app/* prefix.
  • No tenant or organization layer. There are exactly three roles — customer, vendor, admin. A customer account is one row in users, not a member of some larger entity. The admin "Tenant" screen is customer-account management, nothing more.
  • The existing API-key system is untouched. The new login system is a separate, parallel path for the web app — server-to-server integration keeps using API keys exactly as it does today.
  • Every new table is additive. No existing column is removed, renamed, or turned into a foreign key it wasn't before.
